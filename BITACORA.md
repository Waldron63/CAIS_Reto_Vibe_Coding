## Reto 2
- Datos: ~25 minutos (estimado por la hora de los commits: del cierre del Reto 1 a las 08:07 hasta las 08:33) y 3 prompts principales: uno con el enunciado completo del reto y la instrucción de decidir todo sin preguntar, uno para terminar y aclarar que prompts.txt no se sube, y uno para actualizar .gitignore, README y BITACORA.
- Qué hicimos y qué decidió la IA por nosotros: Se pasó de un propietario por mascota a una relación muchos a muchos (mascotas con varios responsables y responsables con varias mascotas). La IA decidió: guardar los responsables como entidad propia, reconocer al mismo responsable por nombre + teléfono para reutilizarlo y no duplicarlo, permitir elegir un responsable ya registrado al crear una mascota, agregar un cuarto módulo "Responsables" con su ficha (modal) que lista todas sus mascotas, borrar al responsable cuando se elimina su última mascota y migrar automáticamente los datos guardados del Reto 1. Además verificó los cuatro criterios en el navegador (registro con dos responsables, ficha de mascota, ficha de responsable y regresión de citas/historial) y reescribió el README (estaba duplicado). Después completó el .gitignore (node_modules, dist, .env, logs, archivos de IDE y del sistema, prompts.txt y datos locales de herramientas de IA) y actualizó README y BITACORA.
- Qué nos sorprendió o salió mal: node_modules estaba versionado en el repo con binarios solo de Windows, por lo que no compila en Mac sin reinstalar (por eso el README usa npm ci); además .gitignore no deja de versionar archivos ya subidos, así que node_modules sigue en el repo hasta ejecutar git rm -r --cached node_modules. El README tenía todo su contenido repetido dos veces. La vista completa tiene dos campos con id="date" (formulario de citas y de notas médicas). El push de main fue rechazado porque David ya había subido su propio commit reto1 (mismo contenido, distinto SHA); el tag reto2 sí subió, pero quedó apuntando a un commit fuera de main. Se resolvió con un rebase de los commits locales sobre origin/main (sin conflictos, árboles idénticos), moviendo el tag reto2 al nuevo commit y sin tocar el reto1 remoto.
- Qué haríamos distinto: Definir desde el Reto 1 el modelo de datos con responsables como entidad separada, tener el .gitignore completo desde el inicio (antes del primer git add .), hacer git pull --rebase antes de cada push y acordar quién sube el tag de cada reto para no pisar el de otra persona. También sumar pruebas automáticas para no depender solo de la verificación manual.

## Reto 3
- Datos: ~30 minutos (estimado: de las 08:50 a las 09:20) y 2 prompts principales: uno con el enunciado del reto, las reglas de trabajo sobre código ajeno y las tareas, y uno para recordar actualizar el README del proyecto heredado. Fork: https://github.com/Waldron63/CAIS12-RetosVibeCodingHeredado
- Qué hicimos y qué decidió la IA por nosotros: Se trabajó sobre el proyecto de otro equipo (monorepo pnpm generado con Replit: API Express + SQLite + React) leyendo solo su README y su código. Se siguió su README al pie de la letra para correrlo, se corrigieron los problemas que impedían o ensuciaban la ejecución y se completó lo que faltaba del Reto 2 (una mascota con varios responsables, ficha de mascota con todos sus responsables y ficha de responsable con todas sus mascotas) antes de implementar el Reto 3 (vista de las visitas de los últimos 30 días y exportación a CSV con mascota, responsable, fecha y motivo). La IA decidió: guardar los responsables como entidad propia y reconocerlos por nombre + teléfono; mantener compatibles el formato antiguo de la API (un solo propietario) y las bases de datos ya creadas (migración automática); guardar la fecha y la hora de las visitas y leerlas con la hora de Bogotá; definir "últimos 30 días" como hoy más los 29 días anteriores; generar el CSV en la API (con BOM para Excel y protección contra fórmulas); añadir pruebas automáticas (28), `pnpm dev` como comando único y actualizar el README del proyecto heredado. No se tocó la bitácora de los compañeros ni se borró nada de lo suyo.
- Qué nos sorprendió o salió mal: Sorprendió que lo entregado no corría tal cual: `pnpm install` terminaba con error en pnpm 12 (scripts de build de esbuild sin aprobar), el README apuntaba a un puerto (5000, ocupado por AirPlay en macOS) y a una variable (LOCAL_API_ORIGIN) que no existen en el código, y `pnpm run build` fallaba por el lienzo de diseño de Replit. El Reto 2 no estaba hecho. Había errores reales: la hora de las visitas se perdía y la fecha se corría un día (una consulta a las 8:30 p. m. quedaba al día siguiente y no contaba como "hoy"), nombres o motivos con solo espacios daban error 500, la edad decimal que permitía el formulario era rechazada por la API con un volcado de Zod, y la búsqueda trataba `%` y `_` como comodines. Quedaron restos de plantilla sin usar (`lib/db` de Postgres y un hook post-merge que siempre falla). No pudimos reproducir el fallo del frontend que ellos reportaron: en macOS con Node 24 y pnpm 12 arrancó bien incluso con el instalador en error. Salvavidas (1 pregunta de 60 s): sin usar; la pregunta sugerida es "¿Con qué comando, versión de Node y pnpm, y con qué error les falló el frontend en la fase 2?".
- Qué haríamos distinto: Cronometrar desde el inicio los 5 minutos para correr el proyecto heredado y apuntar cada tropiezo como hallazgo, escribir las pruebas antes de cambiar el código, no confiar en el README sin contrastarlo con el código y comprobar en el original cada defecto antes de corregirlo. Y, al entregar un proyecto, fijar las versiones de Node y pnpm, probar desde un clon limpio y dejar un comando único para ejecutarlo.
