## Reto 1
- Datos: Nos tomo 20 minutos y 4 prompts, uno por cada funcionalidad y uno para el Readme.md
- Qué hicimos y qué decidió la IA por nosotros: Se hizo un promt con Gemini para darle el contexto de la aplicacion y que dividiera las tres funcionalidades de la aplicacion. La cuota fue de 8% aproximadamente del límite diario.
- Qué nos sorprendió o salió mal: Nos sorprendió el tiempo que le tomó a la IA hacer la aplicación.
- Qué haríamos distinto: Optimizar más el tiempo para lograr probar adecuadamente la aplicación.

## Reto 2
- Datos: ~25 minutos (estimado por la hora de los commits: del cierre del Reto 1 a las 08:07 hasta las 08:33) y 3 prompts principales: uno con el enunciado completo del reto y la instrucción de decidir todo sin preguntar, uno para terminar y aclarar que prompts.txt no se sube, y uno para actualizar .gitignore, README y BITACORA.
- Qué hicimos y qué decidió la IA por nosotros: Se pasó de un propietario por mascota a una relación muchos a muchos (mascotas con varios responsables y responsables con varias mascotas). La IA decidió: guardar los responsables como entidad propia, reconocer al mismo responsable por nombre + teléfono para reutilizarlo y no duplicarlo, permitir elegir un responsable ya registrado al crear una mascota, agregar un cuarto módulo "Responsables" con su ficha (modal) que lista todas sus mascotas, borrar al responsable cuando se elimina su última mascota y migrar automáticamente los datos guardados del Reto 1. Además verificó los cuatro criterios en el navegador (registro con dos responsables, ficha de mascota, ficha de responsable y regresión de citas/historial) y reescribió el README (estaba duplicado). Después completó el .gitignore (node_modules, dist, .env, logs, archivos de IDE y del sistema, prompts.txt y datos locales de herramientas de IA) y actualizó README y BITACORA.
- Qué nos sorprendió o salió mal: node_modules estaba versionado en el repo con binarios solo de Windows, por lo que no compila en Mac sin reinstalar (por eso el README usa npm ci); además .gitignore no deja de versionar archivos ya subidos, así que node_modules sigue en el repo hasta ejecutar git rm -r --cached node_modules. El README tenía todo su contenido repetido dos veces. La vista completa tiene dos campos con id="date" (formulario de citas y de notas médicas). El push de main fue rechazado porque David ya había subido su propio commit reto1 (mismo contenido, distinto SHA); el tag reto2 sí subió, pero quedó apuntando a un commit fuera de main. Se resolvió con un rebase de los commits locales sobre origin/main (sin conflictos, árboles idénticos), moviendo el tag reto2 al nuevo commit y sin tocar el reto1 remoto.
- Qué haríamos distinto: Definir desde el Reto 1 el modelo de datos con responsables como entidad separada, tener el .gitignore completo desde el inicio (antes del primer git add .), hacer git pull --rebase antes de cada push y acordar quién sube el tag de cada reto para no pisar el de otra persona. También sumar pruebas automáticas para no depender solo de la verificación manual.
